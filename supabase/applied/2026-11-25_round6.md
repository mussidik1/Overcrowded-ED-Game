Applied with the owner's approval, from commit `d57115a`, through Claude's Supabase tool (`execute_sql`), not pasted.

1. The whole file was sent once. The tool turned every `\uXXXX` escape into the character itself, so `codeblack.clean_name`'s
   text held real characters where the file has escapes. Every other object matched `supabase/tests/fingerprint.json`; the
   fingerprint showed `clean_name` alone differing.
2. `clean_name` was re-sent with every backslash doubled. Those arrived doubled, which changed the rule, for about a minute.
3. `clean_name` was re-sent as `do $d$ begin execute replace($body$<the file's create statement, with \u written ~u>$body$, '~u', chr(92) || 'u'); end $d$;`,
   so the backslashes were rebuilt inside the database.

Checked afterwards on the live project: `md5(prosrc)` of `clean_name` is `f8adf6a0d7619b06b6e73ad9b8b6a9ab` (length 7958),
the same as the file's body; `codeblack.fingerprint()` is `d6705b15e275614018b897e730e13fa4`, the committed one; the
clean-up job is scheduled and active; "José", "Mary-Kate", "O'Neil", "J.D." and "Ana M." are accepted, and "Bob1",
"a@b.com", "<b>x</b>", "Jane Q Public Jr" and Arabic-Indic digits refused.

Lesson: a migration with `\u` escapes is pasted into the SQL editor, not sent through the tool. Later migrations avoid them.

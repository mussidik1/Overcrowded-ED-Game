# The Code Black database

Code Black keeps two things on a server: class results and the private-testing password gate. Both live in a Supabase project
(`ecpxhcqvgxizdadwumqt`, AWS us-east-1, PostgreSQL 17) that is shared with Case Room. Everything else in the game runs offline
in the browser.

This folder holds every Code Black object in that project, so it can be read, reviewed and rebuilt. Case Room's own tables and
functions (schemas `caseroom` and `golden_hour`, functions `cr_*` and `gh_*`) are not here.

## The files

Applied to the live project on Nov 25, 2026: limits in UTC, daily limits per network and per IPv6 /48, the name rule's invisible characters and scripts, ended classes' codes held 30 days for their own key (at most 30,000 held), a planned code's first result starting it again, invalid calls refused before they count, the clean-up job scheduled again, `cb_health`'s new fields (migrations, backstops, held codes, the fingerprint), when a class was made. |
| `migrations/20261125180000_codeblack_round11.sql` | v0.31.0, the release review: held codes never released early (a new code is `full` past 30,000 held), and the fingerprint hashes function bodies exactly. |
| `applied/` | Notes on how each migration reached the live project, and any repair made there. |

| `tests/run.sh` | The frozen migrations, then a throwaway local Postgres: the baseline, the migrations (the last one twice, and refused over a newer one), the self-recorded name, the refusals, a fresh project, then `privacy_test.sql`. |
| `tests/stubs.sql` | The Supabase pieces the SQL expects: the API roles and their default grants, pgcrypto, a stand-in for pg_cron. |
| `tests/privacy_test.sql` | About 230 checks of the rules, as the browser would meet them. |
| `tests/fingerprint.json` | What the migrations make, object by object (`codeblack.fingerprint_parts()`: each function's body, settings, grants and defaults, each table's columns, constraints, indexes and grants, the clean-up job), and the md5 over all of it (`codeblack.fingerprint()`). `run.sh` checks it against a fresh project, built in another locale, and the migrated baseline, and prints a replacement when the newest migration changes; the deploy compares the live total with it. |
| `tests/client_call.json` | The contract: the exact calls the game makes, every error each function can give, the keys of each answer, and names both sides must accept and refuse. `privacy_test.sql` and `test/class_test.py` both check against it. |
| `../tools/name_ranges.py` | Makes the Unicode lists in the name rule (marks, numbers, enclosing marks, invisible characters) from Python's Unicode tables; `--check` compares them with the newest migration. |

- `npm run db:test` runs the local checks (PostgreSQL 15 or newer, with pgcrypto). CI runs them on PostgreSQL 17, as live.
- `.github/workflows/db-watch.yml` runs the same check once a day from `main`, where a backstop or the held codes past half full, a missing clean-up job or an overdue class fails the run and opens an issue (one at a time: a later failure comments on the open one).
- `npm run db:live` (`test/db_live.js`) checks the live project from outside with the game's public key. The Pages deploy runs it **before** it publishes. It can't run from a Claude cloud container (the network refuses supabase.co). It needs the live database to have the repo's newest migration or a newer one; a run that hits the hourly limit says so and when to re-run; `skip_db_check` on a manual run of the Deploy workflow skips it in an emergency.
- The game reads the project's address and key from `src/backend.json` (the build puts them in the page and in its Content Security Policy). Set `contact` there to show a privacy contact on the About page.

## How class results work (since v0.31.0)

- **Registering a code.** When an instructor picks a shift, the game makes a code and a 16-character **instructor key** (80 random bits, from the browser's secure random source), saves the key on that device (kept 60 days from when the server made the class: its longest life, then the hold, marked unconfirmed until the server answers), and calls `cb_class_new`. The database stores the code with the key's SHA-256 only, and answers when the class was made and when it ends. Registering the same code with the same key again is fine, so a retry after a lost answer is safe; another key gets `taken`, and the game makes a new code. The game shows a code only after the server answers `ok` (never a taken one, nor one refused as busy or full); if the server can't be reached at all (no answer, or no answer in time), or the whole service is full, the instructor may use the code without results, and the game tells them to ask students not to Send (whoever registers the code first would get the results). An error status from in front of the server (a 429 or 503) can be caused by someone else, so it isn't offered then. A class that ended but isn't deleted yet starts afresh when registered again.
- **Sending a result.** After a class-code shift, a student taps Send. `cb_submit` checks everything: the code is registered and live, and the result's version matches the class's (a mismatch answers `unknown`, like a dead code), checked before the call counts toward any limit, so junk sends can't spend a campus's limit; the name is a first name or initials: up to three words of 20 characters in all, each a letter, then letters with their marks in any script, periods, hyphens, apostrophes, middle dots (U+00B7, U+30FB), the Hebrew geresh and gershayim and the Tibetan tsheg; a zero-width joiner or non-joiner only after a letter or mark of the scripts that use one (U+0600 to U+0DFF) and before a letter, or ending a Malayalam word; nothing else (no number of any kind, no symbol, no invisible character, no enclosing mark, no full-width form, no circled, squared or math letter); score 0 to 100, stars 0 to 3, play time up to a day. Stats are rebuilt from known keys only, with whole numbers; anything else is dropped, so a game that sends one more number still works. A refusal names the field. Each result carries its own id from the game, so a retry is kept once. A class holds at most 500 results. Stats include the attending's own patients and deaths, diagnoses, unsafe orders and harm, and radio calls, and whether and when the shift ended early.
- **Reading and deleting.** Only `cb_class_read` and `cb_class_delete`, each with the code and its key, reach a class's results. A wrong key, an unknown code and an expired class get the same answer. The instructor deletes one result (by its id) or all of them (`p_all`).
- **Where it's kept.** The tables are in the `codeblack` schema. The API doesn't expose it, and the public key has no grant on it, so the `cb_` functions are the only way in. They are `SECURITY DEFINER` with `search_path` set to `pg_catalog, pg_temp`, and everything inside is schema-qualified.
- **How long.** A class lasts 14 days until its first result, then 30 days from when it was made; then its results are deleted. Its code is held 30 more days with only its key's hash (no student data), so nobody else, such as a student who knows it, can take it over; its own key can turn it back on, empty. A class that ended with no result (a code made ahead of a class) is started again by a student's first result during the hold, for 30 days from that result, so a planned code works up to 44 days after it was made, on the same game version (results carry the version, and a class only takes its own). Past 30,000 held codes, a new code is refused as `full` (since `20261125180000_codeblack_round11`); no held code is released early, so a flood of throwaway codes can't free a real class's code for someone else. A code that exists still answers `taken` to another key and `ok` to its own. The hourly `codeblack-tidy` job deletes them, and every new code also clears ended classes, so deletion doesn't depend on the job alone. Reads and sends already treat an ended class as gone.
- **Rate limits.** One counter per network, kind and UTC hour (`codeblack.rate`): 60 new codes, 600 sends, 300 reads, 120 wrong-key deletes and 120 health checks per network per hour (plus 30 `cb_health(true)` probes, the deploy's forged-header check); and per UTC day, 200 new codes and 3,000 sends. For IPv6, also per /48 (one site, or one free tunnel-broker allocation): 1,000 new codes and 10,000 sends a day, and 2,000 sends an hour. Deletes with the right key aren't limited. Once a network is over, further refusals write nothing. The network is an HMAC of its address with a random salt that changes every UTC day; counters and salts are deleted within two days. IPv6 counts by /56. The functions run in UTC whatever time zone a request asks for (PostgREST lets a request set one), so a caller can't open more buckets that way.
- **Whose address.** `codeblack.client_addr()` takes Cloudflare's `cf-connecting-ip` first (Cloudflare replaces any value a client sends), then `x-real-ip`, then the first `x-forwarded-for` entry, and only if it parses as an address. This depends on Supabase's gateway; `db_live.js` checks it every deploy (`cb_health` says whether an address was read and whether it is public, and 31 probe calls with forged headers must still hit the limit).
- **Backstops.** About 100,000 live classes (about 25 MB with indexes; held codes don't count, and add up to about 8 MB more at their cap of 30,000) and 300,000 results (about 150 MB, up to about 250 MB if every result carries the most stats), (classes counted, results estimated from the table statistics): far above any real use and well under the free plan's 500 MB, which Case Room shares. Past them, registering and sending answer `full` (a send says whether the class or the whole service is full); a code that already exists, live or held, still answers `taken` to another key and `ok` to its own. `cb_health` reports how full each is, and how full the held codes are (of 30,000), the deploy warns at about half and the daily watch fails (and opens an issue). If someone fills them, delete the junk in the SQL editor, for example live classes with no results made in the attack window (not held codes, which have no results by design): `delete from codeblack.classes c where c.expires_at > now() and c.created_at > '<start>' and not exists (select 1 from codeblack.results r where r.code = c.code);`
- **`cb_health`.** For the deploy's check: the live migration's name and every recorded one (so a skipped migration shows), how many classes are more than two hours past deletion, whether the clean-up job is scheduled, whether the caller's address was read and is a public one (checked whole, against IANA's special-purpose ranges), how full the two backstops and the held codes are, and the fingerprint. No class data. `cb_health(true)` is the probe: it only counts, in its own bucket.

What it can't do: the fingerprint is computed by a function inside the database it describes, so it catches a stale or edited paste, not someone with database access who also edits the fingerprint functions. A player can change their own score in the browser before sending it, and anyone holding a class code can send made-up results to that class under any name. The game says so to instructors ("Not for grading"), and the instructor can delete any result.

## Releasing a database change

The order matters: **database first, then the game.** The deploy refuses to publish a game whose database isn't there yet.

1. Add a new file to `migrations/` named `YYYYMMDDHHMMSS_codeblack_<what>.sql`, later than every applied one. Wrap it in `begin; ... commit;` with `set local lock_timeout`, make it safe to run twice, have it refuse to run without the migration before it and when a newer name is in `codeblack.migrations`, and have it record its own name there (`run.sh` checks the refusals, the second run and the name; the rest is for the reviewer). If the clean-up job matters to it, schedule it again (`cron.schedule` replaces it by name), so re-running the newest migration stays a remedy. Write anything outside ASCII as `\uXXXX` (`run.sh` refuses raw characters: a paste can lose them). Keep the previous release's game and its `test/db_live.js` working (add first, remove a release later), so a rollback deploy still passes. Never edit an applied migration: `run.sh` refuses it.
2. Run `npm run db:test` and add checks to `tests/privacy_test.sql` (and `tests/client_call.json` if a call changes). Push to `3d` and wait for the Tests workflow, its database job on PostgreSQL 17 included, to be green at that commit.
3. The owner approves each change to the live project. He pastes the file into the Supabase SQL editor (or approves the tool call). (Applied through Claude's Supabase tool, the tool turns `\uXXXX` escapes in the text into the characters themselves, which changes the function's text: the round-6 migration's `clean_name` had to be re-sent with the escapes rebuilt in the database. The fingerprint check below catches it.) Check afterwards that `select public.cb_health();` names the new migration and that its `fp` is the `fp` in `tests/fingerprint.json` (a stale paste shows here, before the merge), then add its line to `migrations/applied.sha256` (`sha256sum <file>`, run in `migrations/`) and commit.
4. Merge the game into `main`. The deploy runs `db_live.js` before publishing; if it fails, nothing is published, and the output says why:
   - **not migrated, or a migration skipped:** apply it, re-run.
   - **rate-limited this hour:** re-run after the hour.
   - **the health check didn't answer:** Supabase down or paused (status 0 or 5xx), the key in `src/backend.json` changed (401), or the migration isn't applied (404).
   - **addresses not read, or not public:** Supabase's gateway changed its headers; check `codeblack.client_addr()` against what it now sends. Everyone would otherwise share one rate limit.
   - **the clean-up job missing or paused (a failure: the counters and salts are deleted only by it):** enable pg_cron under Database > Extensions, then `select cron.schedule('codeblack-tidy', '41 * * * *', 'select codeblack.tidy()');`, and if it is paused `select cron.alter_job(jobid, active := true) from cron.job where jobname = 'codeblack-tidy';`.
   - **applied live but not in `applied.sha256`, or the other way round:** add the line (step 3) or apply the migration.
   - **the live database differs from the repo's (the fingerprint):** an older draft was pasted, or something was edited by hand. In the SQL editor, run `select jsonb_pretty(codeblack.fingerprint_parts());` and compare it with `tests/fingerprint.json`: each line names one function, table or the clean-up job. A function: paste the newest migration again from the green commit (it re-creates every function). A table (a column, constraint, index or grant changed by hand) or the job: undo the hand change (the migration that made the table shows what it should be), or, if the change was intended, put it in a new migration. Then re-run.
   - **warnings (not failures):** a deletion more than two hours late, or the backstops or the held codes about half full.
   - In an emergency (Supabase down during a rollback), run the Deploy workflow by hand from `main` with `skip_db_check` ticked and a reason.

Between steps 3 and 4 the live site still runs the previous game. For v0.31.0 that means its Send and Class results fail until the deploy (they used the old open table); the gate is on and nobody uses class results yet.

**Rolling back the game** (`git revert -m 1 <merge>` on `main`) leaves the database as it is, and the deploy's check accepts a database ahead of the game. Rolling back v0.31.0 itself would bring back v0.30.0, whose Send and Class results use the old open table: with this migration applied they simply fail ("Could not send"), and nothing private is exposed. There is no database rollback for v0.31.0: undoing it would reopen the old table.

## The gate

The gate's table and functions (`public.cb_gate`, `cb_gate_on`, `cb_gate_check`) live only in `baseline/`: no migration changes them. **Don't drop them**, at launch or ever: on the gated hosts the game asks `cb_gate_on` before it starts, and without an answer a new visitor sees "Can't reach the server" and can't play. Launch switches the gate off (`gate_on = false`, below). A project rebuilt from `migrations/` alone has no gate: copy the `cb_gate` table and the two `cb_gate_` functions (with their grants) out of the baseline by hand, then set the password.

The gate password's hash is never in this repo. To set or change the password, in the SQL editor:

```sql
update public.cb_gate set pass_hash = extensions.crypt('<the password>', extensions.gen_salt('bf')), updated_at = now() where id = 1;
```

At launch the gate goes off: `update public.cb_gate set gate_on = false where id = 1;`
